# Agent Black Box v0.8 — Operator-selected native transfer (local Mac ACCEPTED)

**Status, October 19, 2026:** I verified my **opt-in, Apple Development-signed, operator-only** bounded file import/export on a real Mac, including the original positive SHA-256 round trip and the five distinct negative checks below. This is a separately tested prototype, **not** an MCP file-transfer tool, a general-purpose import/export product, or a Developer ID/notarized release. My installed macOS `MCP_SANDBOX=required` gateway is a **different**, accepted integration for narrowly scoped synthetic notes.

## What I implemented

- I let the operator choose an import source through the native `NSOpenPanel`; Node, MCP and the XPC worker cannot supply a host file path. My host opens the selected file with `O_NOFOLLOW` and checks a single regular-file link, ownership, file identity, size of 1–2,000 bytes, UTF-8 and SHA-256.
- I require a fresh biometric-only Touch ID decision for the reviewed snapshot, then use a separately App Sandbox-entitled XPC notes worker with a signed incoming host peer requirement. The worker writes exclusively in its private Documents scratch root under an allowlisted `bbx-test-*.txt` name.
- I import with exclusive creation and exact readback. On an unknown outcome after potential dispatch, I do **not** assume rollback or automatically retry.
- I export an explicit worker-owned test note through `NSSavePanel`, another Touch ID decision, `O_EXCL | O_NOFOLLOW`, and file/directory `fsync`; an existing destination cannot be overwritten.
- I validate native code signatures, matching Apple Team IDs, App Sandbox entitlements and lack of network entitlements before running the interactive host. My local HMAC audit records redacted metadata, not selected file paths or contents.

## Evidence collected on my Mac

| Test | On-device result | Evidence boundary |
| --- | --- | --- |
| Native fixture import and separate exported copy | **PASS** | 41-byte positive round trip, independent matching SHA-256, real Touch ID |
| Picker cancellation | **PASS** | Explicit Open Panel cancellation; no XPC commit |
| Oversized generated source | **PASS** | Exact selected 2,001-byte fixture produced `SOURCE_SIZE` before Touch ID/XPC |
| Existing export destination | **PASS** | `O_EXCL` rejection; disposable destination's existing bytes remained unchanged |
| Symbolic-link source | **PASS** | Test-only direct `O_NOFOLLOW` denial **and** AppKit picker returned the selected link's inode; native opener denied before Touch ID/XPC |
| Wrong selected file | **PASS** | Test-only AppKit mode verified the deliberately wrong inode and received native `FIXTURE_MISMATCH` before Touch ID/XPC |

My first *uncontrolled* manual symlink attempt instead imported an unrelated eligible 41-byte file. I did **not** treat that as a symlink bypass or a successful negative test: the file selection was not constrained to the link. I corrected the **test design** by adding dedicated disposable fixture modes, and both later native negative tests passed. The original ambiguous run remains part of the test history; I do not erase it.

The dedicated negative modes build the ordinary host source with `BBX_OPERATOR_NEGATIVE_DIAGNOSTICS` enabled **only for their disposable test executable**. They do not launch XPC, import data, or request Touch ID. A cancelled picker, alternate selection, or AppKit resolving a link to its regular-file target is **not** accepted as evidence of the link-rejection boundary.

## Reproduction

I use `feature/v0.8-native-transfers` and an interactive development Mac. The build-check verifies compilation and signing without opening a file picker or requesting Touch ID:

```bash
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- build-check
```

To reproduce the two additional negative gates, I run one command at a time:

```bash
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-symlink
# In the picker, select ONLY bbx-test-link.txt, not its regular-file target.

MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-wrong-selection
# In the picker, select ONLY bbx-test-other.txt, not the allowed fixture.
```

These modes create and remove their own private test files. They accept only precisely recognized native denials and verified redacted HMAC audit results. If a picker is cancelled, the wrong item is selected, an unexpected Touch ID prompt appears, or the process fails differently, I stop and classify the run as unaccepted or inconclusive rather than calling it a security PASS.

My previously accepted fixture cases are:

```bash
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-import
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-cancel
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-oversize
```

I select **only** the fixture generated for each mode. For `fixture-cancel` I click Cancel before any Touch ID prompt; for `fixture-oversize` I select the exact 2,001-byte file and expect refusal before biometric consent. I never use personal or confidential files for acceptance tests.

For a separate operator-selected, disposable UTF-8 file under 2,000 bytes:

```bash
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- import
# Copy the actual bbx-test-<UUID>.txt identifier printed on an accepted import.
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- export bbx-test-<UUID>.txt
```

I replace the placeholder with the **real accepted note identifier**, select a *new* export destination, approve a separate Touch ID prompt, and compare export bytes independently against the selected input. I do not export if the import has not succeeded.

The already accepted overwrite-negative harness takes the actual imported note identifier:

```bash
MCP_SANDBOX=off npm run mcp:mac-operator-transfer -- fixture-export-overwrite bbx-test-<UUID>.txt
```

It creates its own preexisting test destination, requires denial, and checks that its original bytes remain unchanged. This command is a historical reproduction step, **not** a request to repeat successful acceptance.

## Explicit trust limits

My older pinned RSA Keychain signer authenticates a **fixed 39-byte synthetic handoff**, not arbitrary bytes in this operator-selected flow. I tested the historical integrated RSA suite separately; it does not turn the real-file picker into an independently trusted production approval service.

My HMAC audit and signing/trust material are accessible under the same local-user threat boundary. I have not established independent audit provenance against a compromised Node/controller process, comprehensive swap/race resistance, durable real-file crash recovery, production Keychain ACL isolation, or authoritative external transfer receipts. Unknown operations stay nonretryable and may require manual reconciliation.

Neither legacy nor modern MCP exposes this real-file command. My installed macOS required-mode worker handles **bounded synthetic note** operations only. The Mac prototype uses local Apple Development signing rather than Developer ID/notarized distribution. Synthetic notes may persist in the worker's sandbox Documents directory after accepted tests.
