# Frontend design lab: case-file direction

## Product intent

Make guarded agent behavior understandable to a first-time reader and keep the operator's actual decisions easy to inspect. This sandbox changes the presentation and browser interaction layer; policy, audit, approval, MCP, and native execution contracts remain the original prototype's.

The visual thesis is a physical evidence dossier: warm paper, dense charcoal typography, a restrained red decision stamp, and quiet monospace metadata. The hero gives one concrete sensitive-file example. Case files explain the sequence; architecture shows scope; evidence records expose provenance; the final action opens the operational console. Short entrance motion and control transitions reinforce the page hierarchy; reduced-motion preferences disable animation.

This is a design judgment, not a claim that a particular style is scientifically optimal. The CSS dossier illustration uses selectable text and native geometry, requires no image download, and explains a real request rather than adding decorative imagery.

## Two surfaces, one system

- **Guide `/showcase`:** six immutable cases, shareable case/step URLs, keyboard step navigation, selectable boundary details, and five filterable evidence disclosures. No API calls or execution.
- **Console `/`:** session statistics, grouped activity, decision inspector, one-time approvals, policy list, and the real Ollama tool loop. The scripted demo records nine actual guarded requests. Counts come from the existing backend, never fixed demo metrics.
- **Shared tokens:** `public/design-system.css` defines typography, surfaces, semantic colors, focus, buttons, statuses, and reduced motion. Surface-specific CSS contains layout.

The console distinguishes an allowed policy decision from successful execution, in-progress work, uncertain outcomes, simulation, and failure. If data cannot be verified or loaded, counters become unavailable rather than retaining apparently current values. Stream connectivity and audit integrity are separate signals. Approval content is rendered exactly as text; unchanged polling does not replace focused approval controls or activity rows.

The table scrolls within its own labeled keyboard-focusable region on small screens. Navigation, mobile controls, visible focus, the skip link, native modal Escape handling, and contrast were checked in the browser. No new application runtime dependencies, hosted fonts, analytics, or external services were added.

## Research applied

Sources consulted October 20, 2026:

- [Anthropic frontend aesthetics](https://platform.claude.com/cookbook/coding-prompting-for-frontend-aesthetics) and [Frontend Design plugin](https://claude.com/marketplace/plugins/frontend-design): intentional typography, composition, and product-specific art direction rather than generic generated interface patterns. Used as creative guidance, not proof of authorship or usability.
- [NN/G usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/): visible status, recognizable navigation, clear actions, constraints, and recovery. Applied through active navigation, explicit reconstruction labels, disabled previous-step state, retry messages, and exact approval review.
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/) and [WAI-ARIA interaction guidance](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/): keyboard access, visible focus, contrast, target sizes, and meaningful state. Case choices use native pressed buttons rather than declaring a tab interface without its full semantics.
- [GOV.UK buttons](https://design-system.service.gov.uk/components/button/): clear action hierarchy and feedback. One primary action per task, descriptive labels, and pending controls disabled while their request is active.
- [USWDS alerts](https://designsystem.digital.gov/components/alert/): status expressed in text with next steps, not color alone. Applied to unavailable data and audit incidents.
- [Baymard navigation scope](https://baymard.com/research-articles/highlight-users-navigation-scope): keep the current location apparent. Applied to console navigation, breadcrumbs, and the selected case. The single-page guide has no section navigation header.

Apple accessibility guidance was checked for relevance, but no detailed Apple-specific claim is relied on: this change is a web interface, not a native control redesign.

## Validation

The dependency-free regression suite remains:

```bash
npm test
```

The optional browser acceptance test uses Playwright. It starts a disposable server and audit workspace, injects only a deterministic model transport, and exercises the real HTTP guard, approval queue, and UI. It does not require Ollama or modify the normal demo workspace.

```bash
# Optional development tooling only; does not change package.json:
npm install --no-save --package-lock=false playwright
npx playwright install chromium
npm run test:browser
```

An existing installation may be selected with `PLAYWRIGHT_MODULE` (module name or absolute package path) and `PLAYWRIGHT_CHROMIUM_EXECUTABLE` (browser executable path).

Acceptance covers case selection/reload, direct keyboard step controls, architecture selection, evidence filters, zero guide API requests, the nine-action real demo, decision filtering and inspection, Escape, one-time approval and denial, focus across polling, skip-link behavior, unavailable-data handling, and horizontal overflow at desktop/tablet/mobile widths down to 320px.

Accessibility audits use temporary axe-core tooling outside the app, with browser injection enabled only for the audit. Automated checks supplement visual and keyboard review; they are not a complete accessibility certification. Historical macOS/Touch ID evidence is linked as recorded evidence and is not rerun by these frontend checks. Real Ollama inference is not claimed by the deterministic browser fixture.

## Simplified showcase refinement

The guide now opens without a navigation header. An unobtrusive console link sits above the hero. Author credit, version/design-lab labels, section numbering, the repeated introduction, and installation instructions have been removed from the page. Evidence provenance remains available inside each disclosure. Tighter section spacing and a dark closing action give the page a shorter, clearer reading path.

Browser workflow acceptance and the 14-state accessibility audit were rerun after this refinement and passed.
